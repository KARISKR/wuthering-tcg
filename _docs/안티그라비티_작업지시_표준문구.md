# 안티그라비티 작업 지시 표준 문구

- 작성: 2026-11-07
- 용도: 작업을 맡길 때마다 **1장의 요청문**을 그대로 붙여넣고, 필요하면 2장을 함께 첨부합니다.
- 배경: WP7·WP8에서 반복된 문제는 "빌드·테스트·grep은 통과했는데 실제 동작이 달라진 것"이었습니다. 예를 들면 효과 알림 718건 → 0건, 레벨업 212건 → 545건, 리플레이 0.45MB → 0.9MB였습니다. 그래서 아래 문구는 **실행해서 숫자로 비교**하게 만드는 데 초점을 둡니다.

## 1. 요청문 (매번 그대로 붙여넣기)

`<...>` 부분만 바꿉니다.

```
첨부 zip의 _docs/명조_대결_TCG_작업_계획서.md 「재발 방지 규칙」과
_docs/안티그라비티_작업지시_표준문구.md 2장을 먼저 읽고 지켜.

이번 작업: <작업 이름, 예: WP10 단계 A만>
범위: <바꿔도 되는 파일/폴더>
범위 밖: <건드리면 안 되는 것, 예: gameEngine.ts 판정 로직, 멀티 메시지 형식>

진행 방식
1. 지금 지시한 단계 하나만 해. 다음 단계로 넘어가지 말고 끝나면 멈춰서 보고해.
2. 코드를 고치기 전에 "지금 동작"을 숫자로 먼저 측정해서 보고서에 적어.
   (이벤트 종류별 발생 건수, 저장 데이터 바이트 크기, 줄 수 등 이번 작업과 관련된 것)
3. 기존 필드·함수·데이터 형식을 지우거나 다른 방식으로 바꿀 때는
   바꾸기 전에 "옛 방식 vs 새 방식 비교 테스트"를 tests/에 먼저 만들고,
   같은 시드 50판 이상에서 차이 0건을 확인한 다음에만 옛 것을 지워.
   차이가 나면 지우지 말고 멈춰서 보고해.
4. 배열·상태 비교 코드를 쓰기 전에 그 값을 만드는 원본 함수를 직접 열어 확인해
   (앞에 쌓이는지 뒤에 쌓이는지, 최대 개수, 한 액션 안에서 여러 일이 같이 일어나는지).
5. 저장·전송되는 데이터(리플레이, 세션, 메시지)는 실제 JSON 크기를 측정하고,
   크기 상한을 테스트(expect(...).toBeLessThan(...))로 박아 둬.
6. 확신이 없거나 지시서와 실제 코드가 다르면 추측하지 말고 멈추고 물어봐.

제출물
- 변경된 전체 소스 zip (node_modules·dist만 제외, 빈 폴더에 풀어 npm ci && npm test && npm run build 확인)
- 보고서: 2장 「보고서 양식」 그대로. 숫자는 전부 명령 실행 결과를 그대로 붙여넣기(요약 금지).
- zip 이름에 "완료"는 그 WP의 완료 기준을 전부 채웠을 때만. 단계만 끝났으면 단계명(예: _WP10-A).
```

## 2. 규칙 (요청문과 함께 첨부)

### 2-1. 이 프로젝트에서 실제로 있었던 실수와 막는 규칙

| 있었던 일 | 왜 못 잡았나 | 규칙 |
|---|---|---|
| 루트 파일 20개가 빠진 zip 제출 | 압축 후 목록을 확인하지 않음 | 빈 폴더에 새로 풀어 `npm ci && npm test && npm run build` |
| 1턴에서 500번 헛도는데 테스트 통과 | 결과가 0건이어도 통과하는 비교(0 === 0) | "끝까지 진행" 테스트는 `GAME_OVER` 도달과 루프 상한 미도달을 확인. 비교 테스트는 양쪽이 0이 아님도 확인 |
| AI 판단에 `Math.random` 남음 | 테스트에서 `Math.random`을 가짜로 덮어씀 | 결정성 테스트에서 난수·시간을 가짜로 덮지 않기 |
| 보고서의 이벤트 목록이 실제 코드와 다름 | 계획서를 보고 보고서를 씀 | 보고서는 실제 코드와 명령 출력 기준 |
| 효과 알림 718건 → 0건 | 로그가 앞에 쌓이는데 뒤를 읽음. 원본 함수 미확인 | 비교 코드를 쓰기 전 원본 함수 열람. **옛/새 비교 테스트 먼저** |
| 레벨업 212건 → 545건, 리더 교체 누락 | "칸 레벨이 오르면 레벨업"으로 추정 | 추정 로직 금지. 엔진이 실제로 처리한 곳에서 신호를 받기 |
| 리플레이 0.45MB → 0.9MB, 5판 뒤 저장 실패 | 지문에 상태 전체를 넣음. 크기 미측정 | 저장·전송 데이터 크기 측정 + 상한 테스트 |
| "Zustand 기반", "588줄" 등 틀린 보고 | 이전 문서 복사 | 숫자·라이브러리명은 실제 파일과 명령 출력으로 |

### 2-2. 옛 방식 vs 새 방식 비교 테스트 만드는 법

1. **바꾸기 전 소스로** 같은 시드 50판 이상을 돌려 기준값을 뽑습니다. 예: 이벤트 종류별 건수, 대상 카드·칸·레벨·설명 단위 목록, 종료 상태. 이 숫자를 테스트 파일에 기대값으로 적습니다.
   - 예시: `tests/fx-events-parity.test.ts` (12판 고정 기대값 + 성질 검사 2개)
2. **화면이 하던 일도 흉내 냅니다.** 예를 들어 옛 화면은 알림을 띄운 뒤 `CLEAR_LAST_EFFECT_EVENT`를 보냈습니다. 이걸 빼고 비교하면 718 대 728처럼 가짜 차이가 납니다.
3. 새 방식으로 바꾼 뒤 같은 테스트가 **차이 0건**으로 통과해야 합니다. 테스트를 고쳐서 맞추는 것은 금지입니다.
4. 일부러 버그를 넣었을 때(예: 옛 버그 코드로 되돌리기) 테스트가 **실패하는지** 한 번 확인하고 보고서에 적습니다. 실패하지 않는 테스트는 지키는 게 없는 테스트입니다.

### 2-3. 크기 상한 (현재 기준)

| 대상 | 현재 실측 | 상한 | 확인 방법 |
|---|---|---|---|
| 리플레이 v2 (`start` + `actions` + 지문) | 약 5KB | 30KB | 테스트에서 `JSON.stringify(v2).length` |
| 상태 지문 `stateFingerprint` | 약 30자 | 64자 | `tests/replay-storage.test.ts` |
| 리플레이 로그(v1) | 0.4~0.5MB | (현재 유지) | 측정값을 보고서에 기재 |
| `GameBoard.tsx` | 608줄 | 800줄 | `wc -l` |
| `src` 전체 `any` 계열 | 85건 | 늘지 않기 | 계획서 자가 점검 5번 |

※ "리플레이 1개 30KB 이하"는 잘못된 기준입니다. 로그만 400KB라 지킬 수 없습니다. 상한은 **v2 부분**에만 적용합니다.

### 2-4. 멈추고 물어봐야 하는 경우
- 지시서의 분류나 설명이 실제 코드와 다를 때. 예: "연출 전용"이라던 필드가 게임 상태 계산에 쓰이고 있음.
- 비교 테스트에서 차이가 0이 아닐 때
- 범위 밖 파일을 고쳐야 할 것 같을 때
- 멀티 메시지 형식, 저장 데이터 형식, D1 테이블을 바꿔야 할 때 (구버전 호환 문제)

## 3. 결과물을 받았을 때 확인할 것 (사용자용)

보고서에서 아래 4가지만 먼저 보면 대부분 걸러집니다.

1. **3장 "옛/새 비교"에 실제 숫자가 있는가.** "동일함", "문제없음" 같은 말만 있으면 다시 요청합니다.
2. **"일부러 버그를 넣었을 때 실패 확인"이 "예"인가.**
3. **4장 크기 측정이 "변경 전/후" 숫자로 있는가.**
4. **한 단계만 했는가.** 여러 단계를 한꺼번에 해 왔으면 검토 범위가 넓어져 놓치기 쉬우므로, 단계별로 나눠 다시 확인합니다.

그리고 결과물은 만든 쪽이 아닌 다른 쪽(별도 세션)에 "옛 버전과 같은 시드로 돌려 숫자를 비교해 줘"라고 검토를 맡기는 흐름을 유지합니다.
