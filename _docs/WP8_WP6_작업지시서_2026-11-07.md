## 0. 맡기는 방법

이 지시서는 **단계 A~F**로 나뉩니다. **한 세션에 한 단계만** 맡깁니다. 각 단계는 끝나면 그 자체로 배포 가능한 상태여야 합니다(테스트·빌드 통과, 게임 정상 진행).

| 단계 | 내용 | 규모 | 선행 |
|---|---|---|---|
| A | 리플레이 v2 기록·재생 (WP6 잔여) | 중 | 없음 |
| B | `BattleSource` 연결 어댑터 + 이벤트 구독 | 중 | A |
| C | 전투 상태 저장소 (`useSyncExternalStore`) | 중 | B |
| D | 연출 큐 `fxQueue` + 등록표 `fxRegistry` 뼈대 | 중 | C |
| E | 연출 하나씩 옮기기 + 연출 전용 필드 삭제 | 대 (연출별로 쪼개도 됨) | D |
| F | 화면 컴포넌트 정리 + 리플레이 화면 통합 | 대 | E |

요청문 예시:
> 첨부 zip의 `_docs/WP8_WP6_작업지시서_2026-11-07.md`에서 **단계 A만** 해줘. `_docs/명조_대결_TCG_작업_계획서.md`의 「재발 방지 규칙」을 지키고, 보고서는 이 지시서 「9. 보고서 형식」대로 써줘.

### 1-1. `GameState`의 `last*`/`deferred*` 필드 11개 분류 (중요)

계획서 원안은 "11개 모두 삭제"였지만, 실제 코드를 보면 셋은 **게임 규칙 상태**이고, 넷은 엔진이 **연출 완료를 기다리는 관문**입니다. 함부로 지우면 규칙이 바뀝니다. 아래 분류를 따르세요.

| 분류 | 필드 | 근거 | 이번 작업에서 |
|---|---|---|---|
| **규칙 상태** | `lastClashWinnerIndex` | 우세 판정 보존 (`tcg.ts:322`) | **삭제 금지**, 그대로 |
| | `deferredChoice`, `deferredChoices` | 전투 대미지 후 처리할 선택 효과 큐. UI가 `OpponentFieldArea`, `PlayerHandDock`에서 읽음 | **삭제 금지**. UI는 셀렉터로만 읽기 |
| **진행 관문** | `lastEffectDraw` | `FINISH_EFFECT_DRAW`(`step.ts:560`)가 이 값으로 다음 선택 효과를 이어 붙이고 게임 종료를 판정. `FINALIZE_END_PHASE`(`step.ts:468`)도 이 값이 있으면 진행하지 않음 | **엔진에 유지**. UI가 직접 읽지 않고 이벤트로 받은 뒤 끝나면 `FINISH_EFFECT_DRAW`를 보냄 |
| | `lastComboStrike` | `FINISH_EFFECT_DRAW`의 게임 종료 판정 조건(`step.ts:567`) | 같음 (`CLEAR_LAST_COMBO_STRIKE`로 완료 신호) |
| | `deferredEffectDraw`, `deferredEffectDraws` | 격돌 결과창이 끝난 뒤 풀리는 효과 드로우 대기열 | **엔진에 유지**. UI 직접 읽기 금지 |
| **순수 연출** | `lastUpgrade` | 표시 후 `CLEAR_LAST_UPGRADE`(`step.ts:536`)로 지움 | **삭제 대상** (단계 E) |
| | `lastEffectEvent` | 표시 후 `CLEAR_LAST_EFFECT_EVENT`(`step.ts:553`)로 지움 | **삭제 대상** |
| | `deferredUpgrade`, `deferredEffectEvent` | 격돌 결과창 뒤에 보여주려고 미뤄 둔 연출 | **삭제 대상**. 미루는 일은 `fxQueue`가 맡음 |

> **2026-11-07 정정 (단계 E 검토 결과):** `lastEffectEvent`는 순수 연출이 아니었다. `resolvePendingChoice`가 이 값으로 대결 결과창의 효과 목록(`battleStepEffects`, 게임 상태)을 채웠다. 또 레벨업·효과 알림 정보는 **상태 비교만으로는 알 수 없다.** 그래서 필드만 지우면 연출이 사라지거나 틀린다.
> 최종 구현: 엔진이 `src/engine/fxSink.ts`로 신호를 내보내고(`emitUpgradeFx`/`emitEffectFx`), `step()`이 액션마다 꺼내 이벤트로 만든다. 멀티 게스트에게는 호스트가 `SYNC_GAME_STATE.fxEvents`로 함께 보낸다. 예전 엔진과의 이벤트 일치는 `tests/fx-events-parity.test.ts`로 고정했다.
> 앞으로 비슷한 필드를 지울 때는 **지우기 전 엔진과 지운 뒤 엔진의 이벤트를 같은 시드로 비교**하는 테스트부터 만든다.

**삭제 대상 필드를 지울 때의 원칙:**
- 지우기 전에 엔진 안 사용처를 모두 찾습니다: `grep -n "lastUpgrade\|deferredUpgrade" src/engine/*.ts`
- 사용처마다 "게임 결과에 영향이 있는지"를 보고서에 적습니다.
- 영향이 있으면 지우지 말고 보고서에 "관문으로 재분류"라고 씁니다.
- 결정성 테스트, 시드 50개 테스트, 리플레이 일치 테스트가 **수정 없이** 통과해야 합니다. 테스트를 고쳐서 통과시키면 안 됩니다. 단, 지운 필드를 비교하던 부분만 빼는 것은 허용합니다.

## 2. 모든 단계 공통 금지·주의

1. **게임 규칙 불변:** `gameEngine.ts`의 판정·대미지·효과 로직은 바꾸지 않습니다. `tests/determinism.test.ts`, `tests/multi-seed-convergence.test.ts`, `tests/step-events.test.ts`는 단계마다 수정 없이 통과해야 합니다.
2. **StrictMode 두 번 호출:**
   - `useGame.ts:47`의 `setGameState`는 같은 `prev`에 대해 결과를 캐시합니다. 이벤트 발행도 **액션당 정확히 1회**여야 합니다.
   - 이벤트를 setState 업데이터 안에서 바로 구독자에게 보내지 마세요. 업데이터는 두 번 불릴 수 있습니다.
   - 액션 1개당 이벤트 묶음 1개만 내보냅니다. 다음 둘 중 하나로 하세요: (1) 액션 id별로 이벤트를 모아 두고 커밋 후에 보내기, (2) `step`을 업데이터 밖에서 실행하기.
3. **멀티 게스트·관전자:** `step`을 돌리지 않습니다. 받은 상태에서 이벤트를 만들려면 `diffEvents(prev, next)`를 씁니다. 같은 상태를 두 번 받으면 이벤트도 두 번 나오지 않게 직전 상태 참조를 비교합니다.
4. **이어하기(저장 세션 불러오기):** `useMultiplayerBattle.ts:137`처럼 저장된 상태로 시작한 게임은 처음부터 다시 만들 수 없습니다. 그런 게임은 리플레이 v2를 기록하지 않거나(`replayable: false`), 기존 v1 방식으로만 저장합니다.
5. **기존 리플레이 호환:** 이미 저장된 v1 리플레이(로그 기반)와 `src/data/sampleReplays.ts`는 계속 재생되어야 합니다. v1 재생 경로(`BattleReplayStage` + `replayTimelineBuilder`)는 **지우지 않습니다**.
6. 엔진 안에서 `Math.random`, `Date.now`, `new Date`, `performance.now` 금지. lint와 `tests/engine-purity.test.ts`가 막습니다. 로그 시각은 `logTimestamp()`를 씁니다.
7. `any`, `as any`, `[key: string]: any`, `@ts-ignore` 새로 추가 금지. 기준 85건(`src` 전체)에서 늘면 안 됩니다.

## 3. 단계 A — 리플레이 v2 기록·재생 (WP6 잔여)

**목표:** 경기를 `{시드, 시작 인자, 액션 목록}`으로 저장하고, 그대로 다시 실행해 **같은 경기**를 재현합니다. 화면 통합은 단계 F에서 하고, 여기서는 데이터와 재생 함수까지만 만듭니다.

**대상 파일:** `src/types/tcg.ts`, `src/engine/gameEngine.ts`(시드 저장 1줄), `src/hooks/useGame.ts`, `src/utils/replayManager.ts`, 신규 `src/engine/replay.ts`, `src/components/GameBoard.tsx`(513행 부근 생성 호출), `functions/api/community.ts`(리플레이 저장), 테스트

**단계**

1. **시드 저장:** `GameState`에 `seed?: number`를 추가하고, `createInitialGameState`가 `rngSeed`를 상태에 넣습니다. 이것만으로는 규칙이 바뀌지 않습니다. 결정성 테스트에서 `seed` 키 비교는 그대로 둡니다(같은 시드면 같으니까).
2. **시작 인자 보관:** `useGame`이 `createInitialGameState`에 넘긴 인자를 `startArgsRef`에 저장합니다. 첫 렌더(`useGame.ts:27`)와 `restartGame`(`:86`) 둘 다입니다.
   - 저장할 인자: `p0PresetKey`, `p1PresetKey`, `gameMode`, `p0CustomDeck`, `p1CustomDeck`, `p0CustomName`, `p1CustomName`, `seed`
   - 덱은 **덱 코드가 아니라 `CustomDeckConfig` 원본 JSON**으로 저장합니다. 캐릭터 카드 id가 덱 설정에서 그대로 오기 때문에, 덱 코드로 되돌리면 id가 달라져 `UPGRADE`·`SWITCH_LEADER` 같은 액션이 엉뚱한 카드를 가리킬 수 있습니다. 액션 카드 id는 엔진이 시드로 다시 만들어서 문제없습니다.
   - `initialSavedGameState`로 시작한 경우 `startArgsRef = null`(재생 불가)입니다.
3. **액션 로그 정리:**
   - `actionLogRef`는 `restartGame`에서 이미 비웁니다(`:96`).
   - 액션은 `step`이 실제로 실행된 경우만 기록합니다. StrictMode 캐시로 업데이터가 두 번 불려도 1회만 기록되는지 확인하세요. 지금은 `dispatch` 밖에서 push해서 1회입니다.
   - 상태를 바꾸지 않는 액션(예: 허용되지 않은 단계에서 온 `END_TURN`)은 기록해도 재생 결과가 같습니다. 그대로 둡니다.
4. **v2 형식:** `replayManager.ts`에 아래 타입을 추가합니다.
   ```ts
   export interface ReplayV2 {
     format: 2;
     engineVersion: string; // CURRENT_GAME_VERSION. 엔진 규칙이 바뀌면 옛 v2는 재생 불일치 가능 → 화면에 경고
     start: {
       p0PresetKey: 'STARTER_ROVER' | 'STARTER_CHIXIA';
       p1PresetKey: 'STARTER_ROVER' | 'STARTER_CHIXIA';
       gameMode: 'AI' | 'SOLO_DUAL' | 'MULTIPLAYER';
       p0Deck: CustomDeckConfig | null;
       p1Deck: CustomDeckConfig | null;
       p0Name?: string;
       p1Name?: string;
       seed: number;
     };
     actions: GameAction[];
     finalFingerprint: string; // 종료 상태 지문 (아래 5번)
   }
   export interface BattleReplayData extends BattleReplaySummary {
     logs: LogItem[]; // v1 호환·목록 표시용으로 계속 저장
     v2?: ReplayV2;
     // ...기존 필드
   }
   ```
   `createBattleReplayData`에 선택 인자 `v2?: ReplayV2`를 추가합니다.
5. **재생 함수 `src/engine/replay.ts`:**
   - `replayToEnd(v2): GameState`: `createInitialGameState(...start, seed)` 후 `actions`를 차례로 `step`.
   - `replayFrames(v2): { state: GameState; events: GameEvent[]; action: GameAction }[]`: 액션마다 상태와 이벤트. 단계 F의 리플레이 화면이 씁니다.
   - `stateFingerprint(state)`: `timestamp` 키를 뺀 JSON의 짧은 해시. `tests/step-events.test.ts`의 `fingerprint`와 같은 규칙을 씁니다.
   - **주의:** 엔진 난수는 모듈 전역입니다(`rng.ts`). 재생은 진행 중인 실전 게임이 없을 때만 실행합니다(게임 종료 후, 리플레이 화면). 실전 도중에 재생 함수를 부르면 실전 난수 상태가 덮어써집니다. 함수 주석에 이 내용을 적으세요.
6. **기록 시점:** `GameBoard.tsx:513` 리플레이 생성부에서 `startArgsRef`가 있으면 v2를 만들어 같이 넣습니다.
   - 멀티는 **방장만** v2를 만듭니다(게스트는 액션 로그가 없음).
   - AI전·연습은 로컬에서 만듭니다.
7. **개발 모드 자가 검증:** `import.meta.env.DEV`일 때만, 게임 종료 시 `replayToEnd(v2)`의 지문과 실제 종료 상태 지문을 비교합니다. 다르면 `console.error('[replay v2 mismatch]', ...)`를 찍습니다.
   - 이 검증은 실전 직후 전역 난수를 다시 시드하므로, 실전 상태를 읽은 **뒤에** 실행합니다.
   - 브라우저에서 AI전 3판을 해서 불일치 0건을 보고서에 적습니다.
8. **서버:** `functions/api/community.ts`의 리플레이 저장(`type=replays` POST)이 `v2`를 상세 행(`replay_detail`)에 같이 저장하게 합니다.
   - 요약 행(`replay`)에는 넣지 않습니다(목록이 무거워짐).
   - 요청 본문이 **512KB를 넘으면 `v2`만 버리고** v1로 저장합니다.
   - 응답 형식은 그대로 유지합니다.
9. **크기 측정:** AI전 1판의 `JSON.stringify(v2).length`를 보고서에 적습니다. 512KB에 가까우면 덱 JSON의 긴 설명문 등을 빼는 방안을 제안만 하고, 구현하지 않습니다.

## 4. 단계 B — `BattleSource` 연결 어댑터 + 이벤트 구독

**목표:** 싱글(AI·연습)·멀티(방장/게스트/관전)·리플레이가 같은 인터페이스로 상태와 이벤트를 내보내게 합니다. 화면은 아직 그대로 두고 연결만 바꿉니다.

**대상:** 신규 `src/battle/source.ts`, `src/battle/LocalSource.ts`, `src/battle/PeerSource.ts`, `src/battle/ReplaySource.ts`, `src/hooks/useGame.ts`, `src/hooks/useMultiplayerBattle.ts`, `src/components/GameBoard.tsx`

**인터페이스**
```ts
export interface BattleSource {
  getState(): GameState;
  /** 상태가 바뀔 때마다 (커밋 후) 1회 호출. events는 그 변경에서 나온 이벤트 */
  subscribe(listener: (state: GameState, events: GameEvent[]) => void): () => void;
  dispatch(action: GameAction): void;
  readonly kind: 'local' | 'peer-host' | 'peer-guest' | 'spectator' | 'replay';
}
```

**단계**

1. **`LocalSource`:** `useGame`의 상태와 `dispatch`를 감쌉니다.
   - 이벤트는 `lastEventsRef`를 렌더 중에 읽지 말고 구독으로 전달합니다. 지금 `GameBoard.tsx:779`가 그렇게 읽고 있고, 이 때문에 lint 경고(`react(refs)`)가 납니다.
   - 공통 주의 2번(액션당 1회)을 테스트로 증명합니다.
2. **`PeerSource`:** 방장 모드는 `LocalSource`에 송신만 덧붙인 것입니다. 게스트·관전 모드는 `SYNC_GAME_STATE`/`SPECTATOR_INIT`로 받은 상태를 `diffEvents(prev, next)`로 이벤트화하고, `dispatch`는 방장에게 `DISPATCH_ACTION`을 보냅니다.
   - 기존 처리(`useMultiplayerBattle.ts:158~192`, 방장 쪽 `:226~` 액션 프록시 14종)를 옮기되, **메시지 형식은 바꾸지 않습니다**. 구버전 클라이언트와 대전할 수 있어야 합니다.
3. **`ReplaySource`:** 단계 A의 `replayFrames(v2)`를 받아 재생, 일시정지, 한 단계 앞·뒤를 지원합니다. `dispatch`는 무시합니다(읽기 전용).
4. `GameBoard`는 `useBattleSource()` 하나에서 상태와 이벤트를 받도록 바꿉니다. 지금 `useGame()`과 `useMultiplayerBattle()`을 직접 쓰는 부분이 대상입니다.

**테스트 (신규 `tests/battle-source.test.ts`)**
- `LocalSource`에 액션 20개를 보내면 구독자 호출 횟수가 상태 변경 횟수와 같고, 이벤트 id에 중복이 없어야 합니다.
- `PeerSource` 게스트 모드에 같은 상태를 두 번 넣으면 두 번째에는 이벤트가 0개여야 합니다.
- `ReplaySource`로 끝까지 재생한 상태가 `replayToEnd`와 같아야 합니다.

## 6. 단계 D — 연출 큐 뼈대

**목표:** 연출 순서 조건을 한곳에 모읍니다. 지금은 아래 GameBoard 곳곳에 흩어져 있습니다.

| 위치 (기준 소스) | 하는 일 |
|---|---|
| `GameBoard.tsx:393` | 효과 드로우 연출 끝 → `handleFinishEffectDraw` |
| `:411`, `:463`, `:746`, `:843`, `:1039` | `lastEffectDraw` / `deferredEffectDraws`가 있으면 입력·진행 보류 |
| `:609~614` | `lastComboStrike` → 연격 오버레이 시작 |
| `:616~640` | `lastUpgrade` → 레벨업 오버레이 (격돌 결과창 동안은 보류) |
| `:946~985` | 연격·레벨업·선택·효과 드로우 진행 중이면 카운트다운 대기 |
| `:1019~1054` | 같은 조건으로 버튼 비활성 |

**대상:** 신규 `src/battle/fxQueue.ts`, `src/battle/fxRegistry.ts`, `src/engine/events.ts`(이벤트 종류 추가)

**단계**
1. `GameEventType`에 효과 드로우 연출용 `EFFECT_DRAW`를 추가하고, `diffEvents`에서 `lastEffectDraw`가 새로 생길 때 내보냅니다. payload에는 `drawId`, `playerIndex`, `cards`를 넣습니다. 이벤트를 추가하면 엔진 id 틱을 소비하므로, 결정성 테스트가 통과하는지 꼭 확인합니다.
2. 등록표:
   ```ts
   type FxEntry = {
     component: React.ComponentType<{ event: GameEvent; onDone: () => void }>;
     blocking: boolean;          // 끝날 때까지 다음 입력·연출을 막음
     durationMs?: number;        // onDone을 안 부르면 이 시간 뒤 자동 종료 (안전장치)
     waitFor?: (s: GameState) => boolean; // 시작 조건 (예: 격돌 결과창이 닫힌 뒤)
     onDoneAction?: (e: GameEvent) => GameAction | null; // 끝나면 엔진에 보낼 완료 신호 (관문 필드용)
   };
   export const fxRegistry: Partial<Record<GameEventType, FxEntry>> = {};
   ```
3. `fxQueue`: 이벤트를 받아 등록된 것만 차례로 재생합니다.
   - `blocking` 연출이 재생 중이면 저장소의 `isFxBlocking = true`가 됩니다. 위 표의 "보류" 조건들은 이 값 하나로 바꿀 수 있어야 합니다(단계 E에서 실제로 바꿈).
   - `durationMs` 안전장치가 있어 연출 컴포넌트가 오류로 `onDone`을 부르지 못해도 게임이 멈추지 않습니다.
4. 이 단계에서는 등록표를 **비워 둡니다.** 기존 연출 경로는 그대로 두고, 큐가 이벤트를 받아 무시하는지만 확인합니다.

**테스트 (`tests/fx-queue.test.ts`)**
- blocking 연출 2개가 순서대로 실행되어야 합니다.
- `onDone`을 부르지 않아도 `durationMs` 뒤에 다음 연출로 넘어가야 합니다(가짜 타이머).
- `waitFor`가 거짓이면 시작하지 않아야 합니다.
- `onDoneAction`이 정확히 1회 dispatch 되어야 합니다.

## 7. 단계 E — 연출 하나씩 옮기기 (필드 정리)

**순서:** 격돌 → 연격 → 레벨업 → 효과 드로우 → 효과 알림 → 나머지(HP 알림, 리더 교체 등). 연출 하나 = 커밋 하나입니다. 세션이 길어지면 "격돌·연격까지"처럼 끊어서 맡겨도 됩니다.

**연출 하나를 옮길 때마다**
1. 해당 오버레이를 `fxRegistry`에 등록합니다(컴포넌트 재사용, 연출 모양은 바꾸지 않음).
2. GameBoard·BattleOverlayHost에 있던 감지 useEffect와 로컬 상태(예: `activeComboStrike`, `activeUpgrade`: `GameBoard.tsx:207~208`)를 지웁니다.
3. 6장(단계 D) 표에서 해당 보류 조건을 `isFxBlocking`으로 바꿉니다.
4. 필드 처리는 1-1 분류를 따릅니다.
   - **순수 연출 필드**(`lastUpgrade`, `lastEffectEvent`, `deferredUpgrade`, `deferredEffectEvent`): 이벤트로 대체한 뒤 `GameState`와 엔진에서 삭제하고, `CLEAR_LAST_UPGRADE`·`CLEAR_LAST_EFFECT_EVENT` 액션도 삭제합니다. 다만 저장된 v2 리플레이에 이 액션이 들어 있을 수 있으니, `step`에서는 **아무것도 하지 않는 액션으로 남깁니다**.
   - **관문 필드**(`lastEffectDraw`, `lastComboStrike`, `deferredEffectDraw(s)`): 엔진에 둡니다. UI는 직접 읽지 않고, 연출이 끝나면 `onDoneAction`으로 `FINISH_EFFECT_DRAW` / `CLEAR_LAST_COMBO_STRIKE`를 보냅니다.
5. `HEAL` 연출을 새로 하나 추가해서 "엔진 이벤트 1줄 + 등록표 1항목"으로 동작하는지 증명합니다(계획서 WP8 완료 기준).
